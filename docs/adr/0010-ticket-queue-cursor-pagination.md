# ADR 0010：工单队列游标分页、搜索与状态筛选

- 状态：Accepted
- 日期：2026-10-12

## 背景

`GET /tickets` 原来只有 `limit` 和 `offset`，前端固定请求 100 条。工单数量增长后会一次拉取全量，无法搜索、无法按状态筛选，offset 在并发写入时还可能出现重复或漏项。

## 决策

1. 使用 `created_at + id` 作为稳定排序和游标，默认按创建时间倒序。
2. 游标是不透明 Base64URL 字符串，客户端不得解析或自行生成。
3. 首次请求使用 `limit`，后续使用 `next_cursor`；服务端多取一条判断是否还有下一页。
4. 保留 `offset` 兼容旧调用，但不允许和 `cursor` 同时使用。
5. 增加 `q` 搜索，匹配 `public_code`、`summary`、`description`；增加 `status` 筛选。
6. `total` 继续返回过滤后的总数，便于队列计数；大规模数据下应改为近似计数或独立统计。
7. 增加 `(created_at, id)` 和 `(status, created_at, id)` 复合索引。

## 为什么不使用 offset 作为主方案

offset 在数据变化时会漂移：新增或删除工单会导致下一页重复或跳过。游标把“从哪一条之后继续”编码到请求中，更适合持续变化的队列。

## 代价与限制

- 游标绑定排序字段；如果未来改变排序规则，需要版本化游标；
- PostgreSQL `ilike` 搜索在当前规模足够，但大表需要 trigram 或全文索引；
- 当前只支持单状态筛选，没有多状态和排序自定义；
- 前端仍保留 `total` 用于队列计数，不声称已经支持百万级数据。

## 验证方式

- 两页查询无重复且合并等于全量；
- 搜索 public_code 返回唯一工单；
- 状态筛选只返回对应状态；
- 无效游标返回 400；
- `cursor + offset` 组合返回 400；
- 既有租户隔离、认领和状态机测试不回归。
