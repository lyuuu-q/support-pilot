# 第十八阶段学习说明：会话生命周期与清理

## 为什么会话表也需要保留策略

每次登录都会插入一行 `auth_sessions`，refresh 轮换还会追加新行。长期运行下这张表只增不减，而且里面是"谁能进系统"的信息——既是存储负担，也是安全资产：留着大量已失效的会话记录，等于长期保存不再需要的历史凭据材料。所以它和 Agent 历史一样需要保留期。

## 清理判据为什么只看 expires_at

直觉上会写"删掉被撤销的会话"，但那是不安全的：一个已经登出（revoked）但仍在有效期内的会话，如果被删掉，我们就失去了"这个会话确实被撤销过"的记录；更危险的是任何依赖"行存在即受限"的逻辑都会失准。

本阶段用的是最保守的判据——只删除**已过期**（`expires_at < now - retention_days`）的行。因为 cutoff 永远早于当下，**活跃会话在数学上不可能被选中**，与它是不是 revoked 无关。清理逻辑因此不需要任何"排除活跃会话"的额外条件，也就不会因为条件写漏而误删。

### 与 refresh 有效期的关系

保留期（默认 30 天）应当大于等于 refresh 有效期（默认 14 天），否则长期不用的会话会被清理提前失效——这个行为是安全的（只是多一次登录），但需要运维知道。文档里把它写成了明确取舍，而不是留给读者猜。

## 为什么要能看和能撤销单个会话

"改密码"或"发现设备丢失"时，用户需要一个入口：看到自己在哪些会话里登录着，然后撤销其中一个，或者一键全部撤销。这就是 `GET /auth/sessions`、`POST /auth/sessions/{id}/revoke`、`POST /auth/logout-all` 三个接口的由来，它们都复用第十七阶段的 Cookie + CSRF 机制。

两个细节值得注意：

1. 跨账号撤销返回 **404** 而不是 403：如果返回 403，就等于告诉攻击者"这个会话 id 存在但不属于你"，那是信息泄露。
2. 撤销的如果是当前会话，要顺手清 Cookie：否则浏览器会继续带着一个已失效的 Cookie 发请求，每次都 401，用户看到的是莫名其妙的错误而不是登录页。

## 为什么要写审计和指标

会话撤销是安全相关操作，出问题时第一个要回答的是"谁在什么时候撤销了谁的什么"。审计事件（`auth.session.revoke` / `auth.session.revoke_all`）回答这个问题；指标（会话创建数、撤销数、清理数）回答"最近是否出现异常多的登出"，它们和第十六阶段的 Collector 走同一条 OTLP 通道。

## 一条命令维护两段

```powershell
.\scripts\run_maintenance.ps1                     # 两段清理的 dry-run
.\scripts\run_maintenance.ps1 -Execute            # 真正执行
.\scripts\run_maintenance.ps1 -Execute -SessionsOlderThanDays 45
```

脚本先跑 Agent 历史清理，再跑会话清理，两段 JSON 输出与日志写进被 Git 忽略的 `logs/`。
