# 第十七阶段学习说明：Cookie 会话与 CSRF

## 为什么 localStorage 存令牌不安全

`localStorage` 是页面 JavaScript 可读的。只要攻击者能让浏览器执行一段脚本（第三方依赖、XSS、被污染的 CDN 资源），就能把令牌读走并在别处重放，而且服务端在令牌到期前无法阻止。把令牌放进 `HttpOnly` Cookie 后，脚本**读不到**它，浏览器只在同源请求里自动附带。

代价是出现新的攻击面：Cookie 会被浏览器自动携带，于是"跨站伪造请求"（CSRF）成为可能。所以本阶段是"两件事一起做"——令牌搬进 HttpOnly Cookie，同时补上 CSRF 防护。

## 三个 Cookie 的分工

| Cookie | HttpOnly | 作用 |
|---|---|---|
| `support_pilot_access` | 是 | 短期访问凭据（默认 30 分钟） |
| `support_pilot_refresh` | 是 | 长期刷新凭据（默认 14 天），只在 `/api/v1/auth` 下发送 |
| `support_pilot_csrf` | **否** | 故意让前端读得到，用于双提交校验 |

前两个必须 HttpOnly（脚本不该读），第三个必须可读（前端要把它放进请求头）。

## CSRF 双提交怎么工作

1. 服务端在登录时生成随机 CSRF 令牌，一份写进可读 Cookie，一份哈希后存进会话行；
2. 前端在写请求里带上 `X-CSRF-Token: <Cookie 里的值>`；
3. 服务端校验"请求头 == Cookie"（跨站页面读不到同源 Cookie，所以伪造不出）**并且**"哈希 == 会话行里的 csrf_hash"（令牌必须属于这次会话）。

只做第一步会被子域 Cookie 注入绕过，只做第二步则无法防御无会话的伪造，两者一起才是纵深防御。登录本身不需要 CSRF 头，因为此时还没有会话令牌可以保护。

## 为什么访问令牌要绑定 sid

如果访问令牌只是自包含 JWT，登出就只能等它过期——这正是"无法即时撤销"的老问题。令牌里放一个 `sid` 指向 `auth_sessions` 行，Cookie 路径每次请求都校验该行仍是 `active`，于是登出/撤销立刻生效。Bearer 客户端不带 `sid`，保持无状态兼容。

## 为什么 refresh 要轮换

长期令牌一旦泄露，攻击者可以长期使用。轮换让每次刷新都作废旧令牌：旧值被重放时服务端看到的是已 `revoked` 的行，直接 401。这同时给"令牌被盗用"留下可观测信号。

## 前端为什么要"先 /auth/me，再 refresh 一次"

刷新页面时，访问 Cookie 可能已过期而 refresh Cookie 仍有效。启动逻辑因此是：

1. 调 `/auth/me`；
2. 401 就调一次 `/auth/refresh`（会拿到新的访问与 CSRF Cookie）；
3. 仍失败就显示登录页。

这样用户不会被"明明还在 14 天有效期内"踢出去，也不需要前端自己解析令牌。

## 保留 token 模式的原因

命令行脚本、集成测试和第三方 API 客户端没有"浏览器 Cookie 容器"。强行要求它们走 Cookie 只会把 CSRF 变成空谈。因此登录接口保留 `session_mode="token"`：显式索取 Bearer 令牌，不设 Cookie，也不需要 CSRF 头。前端从不使用它。
